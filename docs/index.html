A game master that routes every action in one request.

In a text RPG you can type anything, and almost none of it needs a large language model to decide what happens. A 2B Strands Decider reads each action locally, plain Python enforces the rules, and Amazon Bedrock only writes the story.

02 / HOW IT WORKS

Three jobs, three owners

Decider

Does the fuzzy work

One request over one encoded game state answers three questions: which mechanic, which item, and is it possible. Each answer carries probabilities and a confidence.

Python

Enforces hard facts

A pure classify() reads those numbers and picks a route. Dice, quantities and spell slots never touch a model.

Bedrock

Writes the prose

It narrates outcomes it is handed and arbitrates only low-confidence turns. Every tool call it proposes passes through ActionGate.

1 · INPUTPlayer types anything
2 · DECIDERmechanic + item_ref + feasible, one local request
3 · classify()plain Python over the numbers
4 · ROUTErefuse · explain · fast · hedged · escalate
5 · NARRATEBedrock phrases the outcome

The trick: options rebuilt from live state

The item question's options are built from the game state every turn: one per item still carried, one per spell, plus none and unlisted. Out of potions, "I drink a healing potion" shifts toward unlisted and is refused. There is no special case for potions anywhere in the code.

Confidence as personality

A confident route narrates decisively. A middling one narrates hesitantly ("you seem to be going for..."). A low one escalates to the arbiter after a visible pause.

03 / TRY THE ROUTER

Move the numbers, watch the route change

This is a browser copy of the decision order in classify(), with the thresholds from my live demo. It does not call a model; you supply the numbers Decider would have returned.

VERDICT
fast
  1. P(unlisted) ≥ ungrounded → refuse in character
  2. feasible < feasible_min → explain why not
  3. mechanic conf. ≥ fast → run it, decisive
  4. mechanic conf. ≥ hedge → run it, hesitant
  5. otherwise → Bedrock arbiter, guarded by ActionGate

Held-out numbers, wins and losses

Calibration is the point. Both of Decider's two tool errors sat below 0.70 confidence; all 18 turns at 0.70 and above were right. Confidence bins: 0.00–0.45 → 2/3, 0.45–0.70 → 5/6, 0.70–0.90 → 9/9, 0.90–1.00 → 9/9. With 27 labelled turns this is a pattern, not a proof.
Where it lost, and caveats

Decider's grounding check missed four of seven cases: "I cast lightning bolt" (P(unlisted) 0.06), a fireball (0.12), a cloak of invisibility (0.17) and a dropped rope (0.14). It snapped unknown spells to the nearest known one. The LLM baseline was clearly better there.

Latencies are not the same measurement: Decider's is server-reported for one request holding three questions; the baseline's is a wall-clock round trip to Bedrock. n = 30, so intervals are wide. Narration is the one place the code does not control, and the narrator sometimes contradicted the outcome it was given.

The tuner picked fast = 0 and hedge = 0 because Decider scored perfectly on the 20 routable dev cases. The live demo used the repo defaults 0.70 and 0.45 instead; those two were not evaluated as a policy on the test split.

06 / REUSE IT

A pattern, not just a game

The decider_patterns/ folder does not depend on the game. Route free-form input to one of N tools with a grounding check, and guard an LLM's proposed tool calls with the same question.

router = ActionRouter(Decider("http://127.0.0.1:8099"),
                      Thresholds(fast=0.7, hedge=0.45, ungrounded=0.3))
decision = router.decide(text, state_text, tools=TOOLS, refs=live_options())
decision.verdict   # fast | fast_hedged | escalate | ungrounded | infeasible

agent = Agent(model=model, tools=my_tools,
              interventions=[ActionGate(decider, state_text, refs=live_options)])

The same shape fits a support bot that must not refund an order the customer does not have, a CLI assistant that must not run a command on a missing file, or a voice menu that must route a caller before a slow model answers.
